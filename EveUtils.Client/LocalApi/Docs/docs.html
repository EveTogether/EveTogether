Connect & Guides

Everything you need to build against the EVE Together local API. Base URL {{BASE_URL}}.

What this is

An opt-in, read-only HTTP API that runs inside the EVE Together client and exposes your own game data — live combat metrics, characters, fits, fleets and doctrines — so you can build stream overlays, widgets and tooling against it. It is one component; widgets are just one use case. The only thing you can write through it is your own saved widgets (see Widgets and OBS); your game data is read-only.

Security model

PropertyBehaviour
BindingListens on 127.0.0.1 only — never on a network interface. Not reachable from other machines.
AccessRead-only for your game data. The only endpoints that write are the widget ones (POST, PUT, DELETE /api/v1/widgets), and they only touch your saved widget configs; the API can never change your fits or fleets.
SecretsNever exposes ESI tokens, granted scopes or credentials — only public game/fit/fleet data.
DefaultOff by default. Enable it and pick the port in Settings → Local API server.
LocationWhere you are is left out by default: location in metrics is null and fleet.metrics sends no Location samples. Turn on Include my location in Settings → Integrations to send it. OPSEC mode leaves it out again while it is on. See Breaking change: Include my location.
HardeningHost-header validation rejects DNS-rebinding. Only same-origin requests are allowed by default — pages served by this API itself, such as /widget; any other origin gets 403, on the WebSocket too, unless it is on the allowlist (localapi.allowedorigins, comma-separated). An optional API key (localapi.apikey) gates /api, /ws and /hub when set.

Getting started

Confirm the server is up, then explore the interactive reference:

# health check
curl {{BASE_URL}}/api/v1/health

# your characters (public identity only)
curl {{BASE_URL}}/api/v1/characters

From a browser widget (e.g. an OBS browser source):

const res = await fetch("{{BASE_URL}}/api/v1/metrics");
const metrics = await res.json();
// [{ characterId, characterName, dpsOut, dpsIn, repIn, repOut, neutIn, neutOut, capIn, capOut, application, ... }]
Load your widget from this API (like /widget) and it is same-origin, so fetch and the WebSocket just work. A page on any other origin is refused unless you add that origin to localapi.allowedorigins. Optionally set localapi.apikey to gate access, then send it as ?key=… or the X-Api-Key header.

GET /api/v1/widgetsThe built-in widget presets (fixed ids such as live-dps, read-only) and your saved widgets, each with its config, the URL to load in OBS and its width × height.
POST /api/v1/widgetsSave a widget config as a new widget. Customizing a preset always makes such a copy under a new id.
PUT / DELETE /api/v1/widgets/{id}Change or delete a saved widget. Presets answer 409 with PRESET_READ_ONLY.
GET /api/v1/killmails/latestYour newest kills and losses, newest first. ?kind=all|kills|losses (default all), ?limit=1-25 (default 1). Each row: kill/loss, ship, ISK, attacker count, time, linked run, final blow, and the ESI-resolved (cached) names of victim and corporation. The solar system is only filled in when "Include my location" is on.
GET /api/v1/runs/currentThe activities on the clock right now, one per group of runs flown together, newest first (empty when nothing runs): type, site, abyssal tier + weather, startedAtUtc (tick the clock from it yourself), bounty, loot and total ISK so far, and the crew. signature and system stay null unless "Include my location" is on.
GET /api/v1/runs/daysRun totals per day, for an earnings overview: ?from=YYYY-MM-DD (required) &to=YYYY-MM-DD (default the current day), at most 366 days, answered per day, empty days included. Each day: runs, flown seconds, ISK, ISK/hour and the ISK per source (bounty, loot, rewards, consumables, mining, homefrontpayout, shiploss) — counted like runs/summary, so the days of a month add up to period=month. ?dayStart=HH:mm (default 00:00) sets where a day begins in the client's local time: with 06:00 a run at 23:30 and one at 01:30 are one day, dated by the day it began. The response names the time zone and its UTC offset. ?breakdown=kind adds a split per activity kind. A bad range or time answers 400. Poll it — it is not pushed. No location.
GET /api/v1/runs/summaryRun totals — runs, flown time, ISK, ISK/hour, average per run, best drop, per character — the same figures the app's home and runs overview show. ?period=session|today|week|month (default today; session counts from the app's start or its last reset), ?kind=all|abyssal|combat|mission|mining (default all). kind=abyssal adds a breakdown per tier and weather.
Every widget has its own page at {{BASE_URL}}/w/<id>: transparent, pinned top-left, made for an OBS browser source. OBS cannot send headers, so with an API key set the URL carries it as ?key=… — keep that URL off stream.

The keys a widget's fields and options understand, per preset (the preset's own defaults first). Every preset also takes theme (together, minimal, ticker), accent, background + panelOpacity, scale and characterIds (empty = every own character). The location fields (system, signature, systems) need showLocation too, and only show while the API itself hands out your location. Add ?preview to the URL to keep the kill alert up with your last kill.

Realtime: WebSocket available

A raw WebSocket at {{BASE_URL}}/ws — the recommended route for browser/OBS widgets, no client library needed. On connect you receive a snapshot, then a JSON event stream of { type, data, ts } (ts = unix ms):

{ "type": "snapshot",      "data": { "metrics": [ /* your toon(s) */ ], "fleet": { /* active fleet or null */ },
                                     "history": [ /* the last 5 minutes per toon, see below */ ] },               "ts": ... }
{ "type": "metrics",       "data": [ /* your running toon(s), every second — always, fleet or not */ ],            "ts": ... }
{ "type": "fleet.metrics", "data": { "characterId":…, "fleetId":…, "kind":"Dps", "value":…, "unixMs":… },           "ts": ... }
{ "type": "fleet.changed", "data": { "fleetId":…, "kind":"…", "serverAddress":… },                                  "ts": ... }
{ "type": "widget.config", "data": { "id":"…", "change":"created|updated|deleted", "config": { /* or null */ } },  "ts": ... }
{ "type": "run.changed",   "data": [ /* same as GET /api/v1/runs/current */ ],                                         "ts": ... }
{ "type": "runs.summary",  "data": [ /* one GET /api/v1/runs/summary result per period × kind */ ],                    "ts": ... }
{ "type": "killmail.added", "data": { /* one row of /killmails/latest */ },                                       "ts": ... }

Combat metrics

Each row of metrics (and of GET /api/v1/metrics) carries, per second:

FieldMeaning
dpsOut / dpsInDamage dealt / received, hp/s.
repIn / repOutRemote repairs received / given, hp/s.
neutIn / neutOutEnergy neutralized on you / by you, GJ/s.
capIn / capOutRemote capacitor received / given, GJ/s.
neutPerSecond / capPerSecondThe two directions added together (unchanged from before).
applicationHow well your main weapon lands: { verdict, percent, breakdown }. verdict is idle, notEnoughShots, notMeasurable, adjust (below 55 %), ok, sweetSpot (from 80 %) or learning; percent (0–100) is only set for the three that measure; breakdown names each weapon's own figure.

History on connect

The snapshot also carries history: for each running character the last five minutes, so a graph does not start empty when OBS restarts. One value per intervalSeconds (1), oldest first and the newest last, all arrays the same length (shorter when the character has not been drawn that long). They are the smoothed values the DPS pop-out draws.

{ "characterId":…, "characterName":"…", "intervalSeconds":1,
  "dpsOut":[…], "dpsIn":[…], "repIn":[…], "repOut":[…], "neutIn":[…], "neutOut":[…], "capIn":[…], "capOut":[…] }
These are additions to v1: no existing field changed. Read them as optional so a widget keeps working against an older client.
const ws = new WebSocket("{{BASE_URL}}/ws".replace("http", "ws"));
ws.onmessage = (e) => { const evt = JSON.parse(e.data); /* evt.type, evt.data — update your overlay */ };
metrics streams your own running character(s) every second, fleet or not. fleet.metrics (one sample per member per tick) and fleet.changed only arrive while you are in a fleet. killmail.added fires for a newly imported kill or loss only, never for a backfill of old mails. run.changed and runs.summary arrive whenever a run changes (started, loot, bounty, saved, deleted), the session is reset or a pocket's tier or weather is picked — not on a timer, so read /api/v1/runs/* once on connect. There is no fit.changed event yet.

Realtime: SignalR available

A SignalR hub at {{BASE_URL}}/hub/fleet for richer .NET/JS clients (@microsoft/signalr), with auto-reconnect and groups. Same events as the WebSocket stream, each as a named handler; you receive a snapshot on connect.

import * as signalR from "@microsoft/signalr";
const conn = new signalR.HubConnectionBuilder().withUrl("{{BASE_URL}}/hub/fleet").withAutomaticReconnect().build();
conn.on("snapshot",      (s)    => { /* { metrics:[…], fleet:…, history:[…] } on connect */ });
conn.on("metrics",       (rows) => { /* your toon(s), every second */ });
conn.on("fleet.metrics", (s)    => { /* one sample per member, in a fleet */ });
conn.on("fleet.changed", (c)    => { /* roster/state change, in a fleet */ });
conn.on("widget.config", (w)    => { /* a saved widget was created, changed or deleted */ });
conn.on("run.changed",   (runs) => { /* the activities on the clock, on every run change */ });
conn.on("runs.summary",  (all)  => { /* run totals per period × kind, on every run change */ });
await conn.start();
WebSocket (the section above) covers the browser/OBS case on its own with no dependency; SignalR is for richer .NET/JS clients that want auto-reconnect and a typed client library.

Sample widget available

A ready-to-run live DPS overlay (raw WebSocket, zero dependencies) lives at /widget — drop that URL straight into an OBS browser source, or open it and view source as a starting point for your own.

Widgets and OBS available

The widget manager in the app (Settings → Integrations → Open widget manager…, or the Local API line on Home) lists the eight built-in widgets with a live preview. Each has Copy URL and Open. Customize opens an editor for the name, characters, fields, theme (together, minimal, ticker), accent colour, background (transparent, or a panel with an opacity), size and the preset's options. Saving it makes your own copy under My widgets; the built-in ones never change. A widget you saved keeps its address, and when you change it an open OBS source applies the change by itself (widget.config over the stream), without a reload.

AddressWhat
{{BASE_URL}}/w/<id>The widget page for OBS: transparent, top-left, no status line and no error on stream. The id of a built-in widget is its preset key (live-dps, dps-graph, current-run, run-totals, abyssal-totals, last-killmail, kill-alert, fleet-dps); a saved widget has a 32-character id. An unknown id answers an empty 404, so a stale OBS source shows nothing.
GET /api/v1/widgetsThe widgets with the url to paste into OBS and the width × height to set there.

A refused write answers { "code", "message" }: 400 VALIDATION_FAILED (a name of up to 64 characters is required; at most 32 characters, fields and options each), 404 NOT_FOUND, or 409 PRESET_READ_ONLY when you try to change or delete a built-in widget.

Add a widget to OBS

  1. In OBS, under Sources, click + and pick Browser. Name it after the widget.
  2. Paste the widget's URL into URL (Copy URL in the manager puts it on your clipboard).
  3. Set Width and Height to the size the manager shows (Add to OBS fills them in for you). Leave Custom CSS as it is: the background is set in the manager.
  4. Click OK and drag the widget where you want it.

The API key in the URL

When you set an API key (the manager can create, show, copy and renew it), every /api, /ws, /hub and /w request needs it. OBS cannot send headers, so the widget URL carries it as ?key=…. Anyone who sees that URL has the key: keep it off stream and out of the OBS properties window. The manager warns you when the URL contains it. Saving a new key restarts the Local API, so renew it and paste the new URL into OBS.

OPSEC

While OPSEC mode is on, your location is left out of the API and the widgets, even with Include my location on (see below). Nothing else is masked.

Versioning

The version is in the path: everything is under /api/v1, and GET /api/v1/health returns { "status", "appVersion", "apiVersion" } (apiVersion is v1; appVersion is the app's own version). The WebSocket and the SignalR hub follow the same contract.

  • Additions stay in v1. New endpoints, new fields on existing rows, new event types and new widget presets or field keys can appear in any release. Existing fields keep their name, type and meaning.
  • Read defensively. Ignore fields and event types you do not know, and treat fields added after your first version (history in the snapshot, repIn… in metrics) as optional, so your widget keeps working against an older client.
  • There is no /api/v2. The one change that makes an existing field empty is the location change below; it was made inside v1, on purpose, and is listed in the changelog.
  • Enums in the widget config (preset, theme, background) travel as strings.

Breaking change: Include my location

Until this release the Local API always sent where you are, even with location sharing off (that setting only ever applied to the server). It is now off by default, for the whole Local API. If your own widget or tool reads your system, it gets nothing until you turn on Include my location under Settings → Integrations.
